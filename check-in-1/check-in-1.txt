Programs and Rendering

A program is simply syntactical sugar that evaluates as nested lets with expression at the end, whose final value
is compiled to HTML using the rendering function, defined by recursion as
R(S, text s) = <span> ++ esc(s) ++ </span>
R(S, button s σ) = <button data-on=" ++ x ++ "> ++ esc(s) ++ </button>
where S(σ) = ( , (src x), )
R(S, column [u1 ; . . . ; un ]) = <div class="column">
++ R(S, u1 ) ++ · · · ++ R(S, un ) ++ </div>
R(S, row [u1 ; . . . ; un ]) = <div class="row">
++ R(S, u1 ) ++ · · · ++ R(S, un ) ++ </div>
R(S, dyn σ) = R(S, VS (σ))
where esc escapes the HTML special characters, and the output is indented when printed. The final pipeline describing
the run of a program is as follows:
1. Desugar the program into a single expression eprog : the declarations become nested lets ending in the render
expression, and event x : T becomes let x = sourcex in.
2. Construct the graph: ⟨∅, ∅, eprog ⟩ −→∗ ⟨S0 , I0 , u⟩, where u is a UI value. This runs once, and the graph
never changes afterwards.
3. Initialise: ⟨S0 , I0 , 0⟩ ,→∗ ⟨S1 , ∅, 0⟩, using every update rule except U-Tick. Print the frame h0 = R(S1 , u).
4. For each tick: parse the next CLI line into ε(t + 1), checking that every name is a declared source, every
payload has the declared type, and no source appears twice. Then run
⟨St , ∅, t⟩ ,→ ⟨S ′ , I ′ , t + 1⟩ ,→∗ ⟨St+1 , ∅, t + 1⟩
and compute ht+1 = R(St+1 , u). Print it only if ht+1 ̸= ht .
5. Repeat until the end of the input. A malformed line is reported on standard error and leaves the state
unchanged.
The same u is used for every frame: only the contents of the store change, and dyn nodes are the only places where
the rendered text depends on them.

Reactive semantics and Proofs - TODO

Relevant papers: Flapjax[3] and Embedding Dynamic Dataflow in a Call-by-Value Language[4]
Following the results these papers, our goal is to implement a push-driven dataflow evaluation by maintaining a
reactive dependency graph G to manage signal propagation from sources to sinks.
Initially our sources will only include events input manually from a CLI. These will be parsed by the OCaml
interpreter and, if necessary, a new block of HTML will be output.

4.1

Proofs

We aim to prove Glitch-Freedom: for any topologically sorted evaluation of G we have that ∀v ∈ V the node v is
evaluated at most once. This guarantees that no intermediate inconsistent states are made visible to the user.
